# 模型升级了，KV Cache 还能接着用吗：DeepSeek-V4-Flash 跨版本复用实测

> 论文：[Can KV Cache Be Reused Across Model Updates? A DeepSeek-V4-Flash Case Study](https://arxiv.org/abs/2611.14051)（arXiv:2611.14051v1，2026-11-10 提交，cs.DC/cs.AI）
> 作者：Zhikun Tao、Fangyong Jin、Junping Zhao。第三方研究者的实验报告，论文未附公开代码，本文为**实验级深读**，全部数字回源论文 HTML 全文，核对日期 2026-11-27
> 前作：[把 14B 的 KV 交给 32B](01_cross_model_kv_transfer.md)（同目录，拆解 Heo et al. 的闭式线性映射）。本篇是其自然续篇：映射方案换成了「什么都不做」的直接复用，模型对象换成同一模型的前后版本

## 一、问题：模型在滚动升级，缓存池跟着作废吗

### 1.1 迭代节奏变了

模型的更新方式在变。DeepSeek-V4-Flash 于 2026 年 4 月 24 日发布 preview，7 月 31 日放出 Flash-0731 更新，间隔约三个月，架构与参数量不变，提升来自新一轮 post-training（论文引 DeepSeek 更新日志口径）。GLM-5.3 同样被官方描述为在 GLM-5.2 的基模上做 post-training。

版本在换，应用侧的上下文却不变：system prompt、RAG 里反复命中的文档、批量数据处理任务的公共指令。这些前缀的 KV Cache 已经算好、存在缓存池里。模型一升级，这批缓存是全部作废，还是能让新模型直接接着用？这就是论文的问题。

### 1.2 direct reuse：最激进的一种复用

跨版本复用有几个保守程度递减的选项：重算（最保守）、选择性重算敏感层（DroidSpeak 路线）、线性映射后再用（前作拆解的 Heo et al. 方案）、以及本文研究的 direct reuse，即**不映射、不重算，旧 checkpoint 的缓存直接交给新 checkpoint 续算**。它是最省的方案，也是最挑战兼容性边界的方案。

一个容易混淆的点：这与前作的跨模型（14B→32B）场景不同。这里是同一模型家族、同架构同参数量的前后版本，理论上共享「坐标系」，兼容性应当好得多。论文要测的正是这个「应当」到底剩多少。

### 1.3 三种配置

设 S 为源模型（旧版本）、T 为目标模型（新版本），同一段输入切为共享前缀 P 和问题后缀 Q：

| 配置     | prefill | 续算生成 | 含义                          |
| -------- | ------- | -------- | ----------------------------- |
| Target   | T       | T        | 新模型全程，原生基线          |
| Source   | S       | S        | 旧模型全程，参照              |
| KV Reuse | S       | T        | 旧缓存 + 新模型续算，被测对象 |

对比在「同一前缀、同一问题、同解码设置」下进行；自由生成用贪心解码。DeepSeek 的缓存是复合结构，论文传递的是完整前缀状态：KV anchor、滑窗注意力状态（SWA）、两档压缩态（C4 与其 Indexer 状态、C128）及关联状态包，不只是常规 K/V 张量。

## 二、四个模型对的总扫描：有人稳、有人涨、有人崩

### 2.1 任务与口径

检索评测用受控 key-value NIAH：前缀长度 512 到 32K 共六档，每档 8 条独立历史 × 24 查询 = 192 条，记录密度约每 16 token 一条，key 和 value 都设计成单 token。判分用答案前缀准确率：回复去首尾空白后以正确 value 开头即算对，请求失败计 0 分。

### 2.2 结果：四个模型对三种命运

| 模型对                           | 32K 处 Target → KV Reuse                   | 32K 处有害翻转率 HFR |
| -------------------------------- | ------------------------------------------ | -------------------- |
| GLM-5.2 → GLM-5.3                | 86.46% → 90.62%                            | 4.22%                |
| DeepSeek-V4.1-Flash → Flash-1017 | 97.92% → 97.92%（全程差距 ≤1.04pp）        | **0.53%**            |
| DeepSeek-V4-Flash → Flash-0731   | 25.52% → 31.25%（但低于 Source 的 55.73%） | 26.53%               |
| Qwen3-30B-A3B → Instruct-2507    | 55.21% → **13.02%**                        | **78.30%**           |

三种命运一目了然。GLM 与 V4.1 这类检索能力强的模型，复用近乎无损；Qwen 即使做了 RoPE 相位对齐，32K 也崩掉四分之三。总体结论：**模型自身的检索越强、版本间隔的行为漂移越小，direct reuse 越可用**。HFR（harmful flip rate）统计的是「Target 答对、复用答错」的比例，比总准确率更贴近复用的真实风险。

### 2.3 总精度提升也会掩盖损失

V4-Flash 一对出现了反直觉现象：32K 处复用反而把 Target 的 25.52% 抬到 31.25%，看似复用是改善。拆开看，复用弄错了 Target 49 个答对中的 13 个，同时修复了 24 个错误。总账为正，细账里有得有失。只看 accuracy 会把「破 13」藏起来，这也是 HFR 存在的理由。

### 2.4 V4.1 延伸到 512K

V4.1-Flash 一对被延伸到 64K–512K：64K 处复用 94.79% 对 Target 95.83%，几乎贴住；128K–512K 的差距分别为 5.21、8.33、4.69 个百分点，但 512K 复用仍有 61.46%（Target 66.15%，Source 57.81%）。复用的额外损失不随长度单调增长，长前缀检索能力大体保留。

### 2.5 Qwen 的 0 分是协议产物

一个口径细节：Qwen 一对里 Source 计 0 分，原因是它的 thinking 风格输出在 8 token 预算内没吐出答案，触发答案前缀协议的失败计 0。这是评测协议的产物，不说明模型检索能力为零。但同一条旧缓存交给新模型，512 处能拿到 80.21%，说明缓存的表示价值与源的答案格式是两回事。

## 三、收益与代价

### 3.1 TTFT：前缀越长越划算，短前缀是负加速

主研究 585 例（BABILong 300、HotpotQA 100、2WikiMQA 100、MultiFieldQA-en 85），TTFT 采用「源缓存已备好」口径：从目标续算请求发出到首个非空 token，含缓存查找、加载、恢复与目标剩余计算，不含源 prefill 与模型启动；Target 侧按无前缀命中的冷请求计。每请求只计时一次。

| Benchmark       | 前缀中位长度 | 中位 TTFT 加速 | 分数变化                                      |
| --------------- | ------------ | -------------- | --------------------------------------------- |
| HotpotQA        | 14.3K        | **5.08×**      | F1 69.3 → 66.3（配对 -3.0，CI [-6.6, -0.1]）  |
| 2WikiMQA        | 6.4K         | 2.10×          | F1 61.7 → 54.7（配对 -7.0，CI [-12.7, -1.5]） |
| MultiFieldQA-en | 7.7K         | 2.51×          | F1 45.9 → 46.2（持平）                        |
| BABILong        | 1.7K         | **0.86×**      | accuracy 59.0 → 58.7                          |

规律直白：**省的是前缀 prefill，前缀越长省得越多；前缀太短，缓存存取开销反超**，BABILong 出现 0.86× 的负加速。复用收益的下界不是零，是负数。

### 3.2 质量：multi-hop 最受伤

四个 benchmark 里，BABILong 与 MultiFieldQA-en 分数持平，两个多跳任务 HotpotQA、2WikiMQA 分别掉 3 和 7 个 F1 点。合理的解释是：多跳答案依赖对缓存中多条记录的精确组合，跨版本漂移更容易破坏组合过程。后文 FCD 的任务分化与这个观察一致。

## 四、缓存里存着指令遵循状态

### 4.1 Flash 注入 Base：0% → 91.15%

这组实验把 Flash 的缓存分别注入训练谱系两端的接收者：更早的 Flash-Base 和更晚的 Flash-0731，接收者权重完全不动，只换前缀状态。

Base 的结果最具戏剧性：用它自己的缓存，模型倾向于复述问题，答案前缀准确率 0%；换上 Flash 的缓存，512/2K/4K 处分别达到 88.02%、91.15%、81.77%，16K 仍有 61.46%。注入 Flash 缓存也全面抬升了 Flash-0731 的检索（16K 从 50.52% 到 65.10%）。

### 4.2 缓存是内容与指令的联合加工品

前缀里既有记录本身，也有「只回答 value」的指令。Flash 的缓存把两者一起编码了：Base 拿到的不只是记录的表示，还有 Flash 对「该如何作答」的处理状态。所以换缓存等于换掉了一段「预加工好的理解」，接收者的答案行为随之改变。这条发现对缓存池设计的含义很直接：**缓存条目不是与模型无关的「上下文资产」，它是某个具体 checkpoint 的加工产物**。

## 五、首 token 一致不算数

### 5.1 首 token 一致与整段一致的裂缝

对 Flash → Flash-0731 的生成做逐序列对比：检索回复 85.4% 完全一致，仅 3.1% 在首 token 后分叉。自然 QA 则完全不同：MultiFieldQA-en 首 token 一致率 87.5%，但 46.2% 的回复后来分了叉；HotpotQA 24.0%、2WikiMQA 28.6% 后分叉。首 token 一致率作为复用安全性的监控指标，信息量不足。

### 5.2 两个案例

论文给了两个具体例子。其一是乐队问题，两个配置都答出 Switchfoot，Target 随即停止，复用版补了一句 "is still together."，与单词标准答案相比 F1 从 1.00 掉到 0.40。其二是「Thomas E. Noell 的父亲在哪里去世」，Target 答华盛顿特区，复用版答圣路易斯，人物与地点的对应关系被换了，F1 从 0.67 到 0.00。前者是停止行为漂移，后者是答案内容漂移。

### 5.3 停止行为的漂移有统计支撑

补充探针测了 EOS 的分数领先量（EOS 对最强续写 token 的 margin）：HotpotQA 随机 20 例中 17 例下降，均值 -1.131；2WikiMQA 随机 20 例中 15 例下降，均值 -1.150。复用状态整体上让 EOS 的领先量下降，模型更倾向继续生成，这与 5.2 的补话案例吻合。

## 六、机制：漂移从哪来

### 6.1 FCD：检索与续写的两条曲线

论文提出 Functional Cache Divergence（FCD）：固定目标模型、后续输入 token 与预测位置，比较「用自己的缓存」与「用源缓存」时下一个 token 全分布的 Jensen-Shannon 散度，按 100/ln2 缩放到 0–100。它捕捉「选中 token 没变、概率分布已经变了」的情形。

两条曲线截然不同：

| 任务             | 512 处均值 | 32K 处均值              | 走势       |
| ---------------- | ---------- | ----------------------- | ---------- |
| NIAH 检索        | 2.87       | **30.62**（中位 23.51） | 随长度增长 |
| FineWeb-Edu 续写 | 3.04       | 3.51（全程 3.04–3.64）  | 平坦       |

解释与任务性质对得上：NIAH 的答案必须来自缓存里的任意 key-value 关联，前缀越长竞争记录越多，对缓存表征越敏感；自然续写有局部词法与语法线索兜底。同一评测里的另一组数字：Target/Reuse 的 top-1 一致率从 512 处的 96.35% 降到 32K 处的 68.75%。

FCD 高不等于坏：32K 处按配对结果分组，「修复了的错误答案」均值 FCD 63.23，「弄丢的正确答案」66.15，「两次都对」仅 9.99。**大的功能偏移既可能伴随改善也可能伴随损失**，所以论文把 FCD 定位为偏差度量，不做好坏判定。

### 6.2 margin：答案怎么活下来

在 4K NIAH 上看首答案 token 的 gold margin（gold 分数减最强竞争者）：Flash-0731 接收旧缓存后 margin 中位变化 -1.00 logit，但多数正确答案靠原有领先优势存活，修 14 丢 6，准确率 87.50% 升到 91.67%。Flash-Base 则全部查询 margin 上涨，中位 +11.77 logits，准确率从 0 到 81.77%。**窄 margin 的答案最脆弱**，margin 分析把「哪些答案会在复用下翻转」从玄学变成可观测量。

### 6.3 Indexer：选择大变照样答对

DeepSeek 的稀疏注意力靠 Indexer 挑选压缩条目。按 4K/8K/16K/32K 各取四条、共 16 条「原生答错、复用答对」的恢复案例里，Indexer 的 top-k 选择与 Target 的平均重合度从 81.7% 降到 55.4%，深层更低（修正随机基线后，晚层从 50.0% 到 37.1%），但答案全部正确。检索可以容忍缓存条目选择的大幅变化，又一次印证表征保真与任务可用是两个维度。

### 6.4 干预实验：扰动沿层传播

第 37 层的四组合交叉干预（96 查询群体，换输入表征 / 换本层缓存 / 都换）结果：只换本层缓存，注意力输出差异中位 0.019；只换进入本层的 hidden state，0.473；两者都换，0.530。**扰动的大头不在本层缓存，而在前层传播累积后的输入表征里**。修复实验佐证：对四个失败案例，替换 36–42 层的注意力输出能全部救回，只替换这些层的 prefix cache 只救回一个。这也解释了为什么「事后把某几层缓存换回来」修不好答案。

## 七、映射不如直用？

### 7.1 Ridge Mapper 对照结果

论文把前作 Heo et al. 的闭式 ridge 映射适配到 DeepSeek 的复合缓存（覆盖 active window、压缩态、Indexer 态共 43 层，RoPE 前内容坐标联合映射），用 500 篇 FineWeb-Edu 文档校准。结果并不一致占优：

| 前缀 | KV Reuse | Ridge Mapper | 差异                              |
| ---- | -------- | ------------ | --------------------------------- |
| 2K   | 96.35%   | 92.19%       | 映射反而掉 4.16pp                 |
| 16K  | 65.10%   | 59.38%       | 映射掉 5.72pp                     |
| 32K  | 31.25%   | 40.10%       | 映射高 8.85pp（CI [5.21, 12.50]） |

V4.1 延伸到超长前缀后差距更清楚：256K 处映射 52.60% 对直用 72.40%，512K 处 40.10% 对 61.46%。**长前缀下 direct reuse 比校准过的映射更有韧性**；映射只在 Flash 模型对的 32K 单点占优。

### 7.2 与前作的衔接

前作的结论是：跨尺寸模型对之间，线性映射是正确的函数形式，且 mapper 体积与校准成本可控。本篇补上了另一半图景：同家族前后版本之间，映射的收益不稳定，直用可能更好。两条结论合起来指向一个分工：**跨尺寸走映射，跨版本优先直用**。论文已经在同一模型对上做了检索维度的对照（就是 7.1 的表格），但 QA 质量、延迟、校准成本摊销这些维度的同场景系统比较仍缺。

## 八、总评与口径折扣

### 8.1 分级判断

| 判断                                                                                    | 依据强度                                 |
| --------------------------------------------------------------------------------------- | ---------------------------------------- |
| 同家族跨版本 direct reuse 在检索强的模型对上近乎无损（GLM、V4.1），512K 处仍保有 61.46% | 铁证（1,152 + 1,920 条受控查询）         |
| 缓存已备好时 TTFT 加速 2.10–5.08×，短前缀负加速 0.86×                                   | 铁证（口径：缓存已备好、每请求单次计时） |
| 缓存携带源的指令遵循状态，注入可改变接收者行为                                          | 铁证（Base 0%→91.15% 权重不动）          |
| multi-hop QA 掉 3–7 F1，首 token 一致不能代表答案一致                                   | 铁证（585 例 + 逐序列对比）              |
| 检索 FCD 随长度增长、续写平坦                                                           | 铁证（1,152 检索 + 12,288 续写配对位置） |
| 漂移主要沿层传播而非本层缓存所致                                                        | 旁证（仅检 27/37/42 三层、96 查询）      |
| 跨版本优先直用、跨尺寸才走映射                                                          | 推断（两个研究并置，无同场景对照）       |

### 8.2 四条审慎点

1. **Case study 局限**：深度分析（QA、干预、FCD）只做了 DeepSeek-V4-Flash 一对，四个模型对的检索扫描不能替代逐对验证；换一对模型，HFR 可能重排。
2. **协议产物要认出来**：Qwen Source 计 0 分是 thinking 格式吃满 8 token 预算所致；答案前缀协议对带格式前缀的输出（Base 常先吐空白/格式 token）也偏保守，论文用 readout 诊断补了严格匹配口径。
3. **延迟数字的口径**：TTFT 是「源缓存已备好」的续算路径，源 prefill 与模型启动不计，每请求只计时一次；跨版本对比还混入了同版本服务交接自身的差异（同版本恢复在 MultiFieldQA-en 的完整序列一致率仅 52/85）。
4. **512K 延伸的构造差异**：512K 需要的 65,536 个互异词超出 53,162 的词池，同一 token 会在不同记录里兼任 key 与 value，与前档构造不完全同质（key 与 value 各自仍唯一）。

### 8.3 对缓存湖系统的落地判断

对 LMCache、Mooncake 这类把 KV 缓存做成池化资产的系统，这篇论文给出的增量是一组新参数：**缓存条目的模型版本亲和性**。以下推断按论文证据的适用范围给出：

- 缓存索引的键需要带模型版本号；跨版本命中不该默认视为命中，而应标记为「direct reuse 候选」并按模型对分级放行；
- 放行依据建议用检索型探针（NIAH 风格）在目标模型上实测 HFR，32K 长档是最敏感的探针长度；首 token 一致率不适合做监控指标；
- 任务路由可按论文口径粗分：长前缀、检索抽取型（RAG 命中、模板化文档问答）收益风险比最好；多跳 QA 有 3–7 F1 的实付代价；短前缀一律走原生 prefill，负加速是实测过的；
- FCD 的实现成本（全分布对比）偏高，生产上更可能用答案级配对抽检替代，margin 类探针（如 gold token 领先量）是折中选项。

论文自己在结尾列的后续方向也值得跟踪：覆盖更多任务与解码设置、在复用前预测会影响 token 决策的漂移、以及把缓存中的事实内容与响应指令成分拆开归因。
