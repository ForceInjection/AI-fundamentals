# 13 · XTRA：CXL Pod 里统一缓存一致性与并发控制

> SOSP 2026 论文精读笔记。来源：`../papers/13_xtra-cxl-transactions.pdf`（作者版 PDF，Yu Hua 主页，2026-11-14 下载；SOSP '26, Prague, DOI 10.1145/3830418.3843888）。文中数字均为论文口径。

## 一句话

把记录上的锁与版本收进有界协调目录，OCC 冲突检测兼作惰性缓存校验，事务吞吐最高升 15.6 倍。

## 问题与背景

CXL Pod 用 load/store 直连 TB 级共享内存池，最新系统支持 16 主机、8TB 池，访问延迟比 RDMA 低 3~10 倍（§2.1，p.271）。跨主机硬件缓存一致性（HCC）到 CXL 3.0 才引入，依赖设备侧 snoop filter 的有限 SRAM，业界预期 HCC 域只有数百 MB，池内其余部分仍是无硬件一致性的 NHCC 区（§2.1，p.271）。

分布式事务在此背景下面临三个挑战（§1，p.269-270）。C1 一致性域有限：跨主机 CAS 不可用，锁与版本失去硬件原子性支撑。C2 逐记录元数据的协调代价高：代表工作 Tigon（SOSP'25）用 on-demand sharing 把记录迁入共享池、元数据放进 HCC 区，作者在 8 主机测试床测得，数据集涨到 500 万与 4000 万键时吞吐跌 4.3 倍与 30 倍，P99 涨 4.2 倍与 588 倍，根因是 Perfect Hit（全部远程访问命中 HCC）从 100% 塌到 34% 再趋近零，stall 占比超 90%（§2.2，p.272，Fig.1/2）。C3 CXL 内存访问比本地 DRAM 慢 2 倍以上、带宽受 PCIe 限制，必须吃本地缓存（§1，p.270）。

论文的出发点是两条观察（§2.3，p.272-273）：其一，任一时刻参与活跃并发控制的记录数有界，同步状态不必长在数据上，可集中进一个小目录；其二，OCC 版本校验与缓存一致性回答同一个问题（对象自上次读取后是否变过），事务校验通过即缓存仍新鲜，两套机制可以合一。

## 核心设计

**协调目录（CD）**。共享内存分两个逻辑区：TB 级 NHCC 数据面放数据表与索引，小的 CD 控制面放同步状态（§3，p.273）。CD 是 64 位槽数组：50 位版本、1 位锁标志、5 位主机号、8 位线程号，支持 32 主机各 256 线程（§4.1，p.273）。每个对象（数据记录、索引节点）用池内偏移指针做规范标识，slot = Hash(offset) mod N 确定性映射（§4.1，p.273）。目录大小 N 由预期并发度与 HCC 预算决定，与数据集规模无关：8MB 目录有 100 万槽，8192 线程各访问十几个对象时负载因子低于 10%，误冲突概率可忽略（§4.1，p.273）。槽冲突只造成假串行化，真冲突不会被漏掉，损失的是并发度不是正确性（§4.1，p.274）。

**解耦 OCC 事务协议**。三阶段（§4.2，p.274，Fig.5）：执行期投机运行，读对象时记下 CD 槽版本，全程无锁，更新缓存在本地写集；提交前按写集拿槽锁（CXL 3.0 用 HCC 区内 CAS），再校验读集各槽版本未变，不符则释放写锁中止；提交时先刷 redo log 到共享 NHCC 区，用 CLWB + SFENCE 围栏落更新，最后一条 CXL 写同时清锁位并推进版本（§4.2，p.274）。安全性：读写冲突的两个事务必然映射到同一槽，一方持锁提交，另一方必观测到锁位或版本差异而中止（§4.2，p.274-275）。槽锁可重入，同一事务写两个同槽对象不会自锁；锁在全部写集全局可见后才释放（§4.2，p.275）。索引遍历用乐观蟹行：跟随指针后复验父节点槽状态，变了从根重走，读路径无锁（§4.2，p.275）。

**事务驱动的统一缓存一致性**。写方提交只推进 CD 版本，不发失效消息；读方验证版本相等即认定 CPU 缓存副本新鲜。两个错配由 Shadow Directory（SD）补齐（§4.3，p.275-276）：时间上 OCC 校验只活一个事务的生命周期，缓存一致性要求持续有效；空间上事务是逻辑隔离，LLC 是主机内所有线程物理共享的。SD 是主机本地的 CD 镜像，第 i 个影子槽对应第 i 个 CD 槽，8 字节头部存 V_shadow、锁字段与有效表项数，每个 8 字节追踪项存 48 位 NHCC 地址、14 位 cacheline 数、2 位访问计数，M=7 时一个影子槽恰塞进一条 64B cacheline，扫描在读锁内完成（§4.3，p.276）。三种情形（§4.3，p.276）：版本相等且已追踪，直接用缓存副本，无锁快路径；版本相等但未追踪，不信任本地缓存，先 CLFLUSH 清理再装追踪项（sanitization-on-entry，影子槽写锁保护）；本地版本落后，把 V_shadow 推进到 V_slot、清空全部追踪项、回到清理步骤。SD 无需持久化，主机崩溃后本地缓存与 SD 一起消失，重启即重建（§4.3，p.276）。可选的 DRAM 缓存层复用同一套版本校验（§4.3，p.276）。

**CXL 2.0 推广**。CD 放进 NHCC 区：读槽前先 CLFLUSH 防本地缓存陈旧，CAS 换成基于 Lamport 快速互斥算法的软件锁（§4.4，p.276-277）。解耦让软件互斥可行：逐记录配锁元数据时 8 主机 pod 单主机锁足迹超 512B（互斥空间下界 Ω(N)），XTRA 把同一主机更新的标志位按列主序打进相邻槽的同一 cacheline，免跨主机盲覆写且足迹不随数据集涨（§4.4，p.277）。争用时同主机线程先在本地原子操作上分胜负，每主机最多一人上 CXL 链路争软件锁（§4.4，p.277）。

**故障恢复**。fail-stop 模型，redo log 写前落共享 NHCC 区。恢复两步：扫 CD 找故障主机持有的锁，查其日志缓冲判断每笔事务 redo 是否完整，完整则重放前滚，不完整则仅释放锁中止（§4.5，p.277-278）。

## 效果与代价

评估是模拟的：CXL 3.0 跨主机 HCC 尚无商用硬件，作者按既有方法在双路 Xeon Gold 6530、256GB 本地 DRAM、128GB CXL 2.0 设备的机器上，用 8 个 VM（各 4 核 32GB）模拟 8 主机 pod；VM 间一致性走物理机总线，比真实跨主机 HCC 快，作者认为对齐后公平（§5.1，p.278）。基线：Tigon、Sundial-CXL、Motor（RDMA 共享一切，4 台物理机、ConnectX-5、100Gbps InfiniBand）。HCC 与 CD 均设 200MB。负载：YCSB、SmallBank、TPC-C，三档数据集 S/M/L（Table 1，p.278）。

主要数字（§5.2，p.279）：对 Tigon 吞吐高 1.3~15.6 倍，P50/P99 低 1.3~4.0 倍与 1.2~283.9 倍；对 Motor 吞吐高 1.1~15.5 倍，P99 低 1.3~25.5 倍。数据集从 S 到 L，XTRA 吞吐只降 16.9~45.6%。1 到 8 主机扩展 XTRA 达 3.7~6.1 倍，8 主机处超基线至多 10.9 倍；Tigon 在 2 主机时靠迁移涨 46.8%，3 主机起跌 3.1 倍（§5.4，p.280）。HCC 预算缩到 10MB 时 XTRA 仍比 Tigon 高 1.2~31.5 倍，0MB 时回退 XTRA-NHCC 吞吐降 43.9~53.0%；把 OCC 换成 2PL 后，HCC 缩到 10MB 时 XTRA 对它的优势从 1.2 倍拉开到 90.6 倍（§5.5，p.280-281）。统一一致性单独拆出：对比绕缓存的 NonTemporal 基线，吞吐高 1.5~39 倍，P50/P99 低 1.4~41 倍与 1.5~4.2 倍（§5.6，p.281-282）。

代价：S 规模下 XTRA-NHCC 比 Tigon 慢 20.8~39.0%，软件互斥加显式缓存失效打不过硬件原子（§5.2，p.279）；极端写偏斜（SmallBank θ=0.99）下所有系统退化，Motor 在 θ>0.9 就因活锁跑不完，OCC 在重写负载上也略输 2PL（§5.3，p.280 与 §5.5，p.281）；DRAM 缓存在 KVS/SmallBank 上是负收益，只在 TPC-C 带来 11.2% 吞吐与 29.6% P99 改善（§5.6，p.282）。论文自认的局限（§6，p.281-282）：共享数据须装得进 CXL 池，超出后的容量分层策略留作未来工作；内存池自身故障在模型之外。

## 总评

这篇论文回答的问题很具体：HCC 域只有几百 MB 时，TB 级 CXL 池上的分布式事务还能不能做成共享内存语义。答案是能，方法是同步状态与数据解耦，再加一致性校验与事务校验合一。两条机制各有出处（目录式同步、OCC 版本校验），新意在于指出两者的校验语义重合、可以只付一次代价，并给出 CD 加 SD 的完整工程方案，连 CXL 2.0 无硬件原子时的软件互斥内存布局都做了。评估有几点要打折：CXL 3.0 环境是 VM 模拟，VM 间一致性强于真实跨主机 HCC；100 万槽 CD 在更大主机数或更长事务下的负载因子只给了 8192 线程一档的推算；Motor 跑在原生 RDMA 环境，硬件条件不对齐；Tigon 侧 200MB HCC、XTRA 侧 200MB CD 的等额设置依赖作者的公平性论证。

对数据库与存储系统读者，这条路线的价值在于把缓存一致性从硬件义务降级成软件校验：写路径零失效消息，读路径多一次版本比对。代价是失效粒度从 cacheline 粗化到 CD 槽，未追踪对象首次访问要付一次全量 CLFLUSH。CXL pod 规模事务离现实仍有距离：CXL 3.0 HCC 本身尚未商用，连论文自己的评估环境都是模拟的；但 XTRA-NHCC 在 CXL 2.0 上的回退版本说明这套设计不押注硬件到位，这一点比吞吐数字更有长期价值。

## 疑点与待核

- §4.2（p.275）原文「without over-heading per-slot reentrancy counters」，over-heading 疑为 overhead 笔误，不影响理解。
- 摘要的 15.6 倍与 4.0×/283.9× 取自 §5.2 区间的最好端点，引用时需注明工况。
- Perfect Hit、stall time 沿用 Tigon 的内部度量口径，§2.2 的复现环境与 §5.1 配置是否逐项一致未说明。
- SD 追踪表写满后按 2 位计数的频次替换只有一句话，替换精度与抖动没有评估数据。
- 8 主机 pod 模拟沿用 Tigon [18, 75] 的方法，VM 数超过物理核时的调度干扰如何控制未提。
