# 07 · Skill VM：Agent Skill 的一次编写、处处高效执行

> SOSP 2026 论文精读笔记。来源：`../papers/07_skill-vm.pdf`（IPADS 公开版，2026-11-14 下载；SOSP '26, Prague, pp.482-498, DOI 10.1145/3830418.3843874）。文中数字均为论文口径；实现 36,200 行 TypeScript，开源于 github.com/SJTU-IPADS/SkVM。论文系统名为 SkLLVM。

## 一句话

把 Agent Skill 当源代码、把 LLM 当异构处理器，套用经典编译技术做 AOT + JIT 编译：安装时按「目标模型 + harness + 环境」生成特化变体，运行时再固化热代码路径，让同一个技能在不同模型上都能跑得又对又省。

## 问题与背景

作者先量了生态：两个分发平台（clawhub.ai 28,990 个 + skills.sh 89,280 个）共 118,000 个技能，其中 89% 下载量不足 100 次，长尾严重（§2.3）。对 15,063 个下载过百的技能做 LLM 辅助分类：52% 是工具用法说明（tool-reference）、28% 是过程性指导（procedural）、20% 是内容生成。技能由三层构成：metadata（名称、描述、触发条件）、instructions（自然语言工作流）、bundled resources（脚本、引用、模板）（§2.1）。

问题在于技能被当成裸文本直接塞进上下文，文本里隐含了对模型能力、harness 能力和机器环境的假设，假设错了就出三种失配（§2.4）：

- **P1 模型失配**：同一技能跨模型得分差异巨大；启用技能反而让 15% 的任务变差、17% 的任务不变，至少一类任务 87% 无改善。典型案例：pptx-creation 技能推荐 PptxGenJS（JS 库），Claude Opus 4.6 与 Gemini 3 Flash 照做拿 100 分，devstral-small 在 OpenCode 里却反复执行 CLI 命令、换用 python-pptx 得 95 分——技能假设模型能分辨「库与 CLI」，弱模型分不清。
- **P2 harness 失配**：同一模型换 harness 结果就变，harness 引起的方差与模型间方差相当。Gemini 3 Flash 在 BareAgent 上工作流调度任务 100 分，在 OpenCode 上 0 分，原因是一个畸形 JSON key 让输出不可解析：OpenCode 前置的长系统提示与长文档改变了模型的输出格式。
- **P3 环境失配**：53% 的技能要求至少一个外部包或工具，但只有 19% 声明了依赖，40% 以上在指令与脚本里实际用到而未声明。缺依赖时弱模型成功率掉 33-67%，强模型（Claude Opus 4.6）能自行诊断安装但要多产 56-69% token。

## 核心设计

SkLLVM 的框架是 Figure 1 那个类比：技能是代码，LLM 是异构处理器，当前做法等价于只有解释执行。系统分 AOT 编译器（安装时）与 JIT 运行时（执行期）两层（§3）。

**AOT 编译三个 pass**：

1. **能力化编译（§4.1）**：定义 26 个原语能力（gen_code、reason、tool_exec、follow_procedures 等），每个能力分 L1/L2/L3 三级熟练度。能力集从 50 个种子技能出发由 LLM 辅助分解、人工复核，收敛条件是覆盖 95% 语料的需求、且新能力必须出现在至少 1% 的语料中。编译时左侧提取技能的能力需求，右侧用微基准剖析目标（模型+harness 组合）的实际能力档位并缓存复用，然后按差距选变换：首选 **compensation**（目标低一级时加示例、显式化指令、收紧约束，保留原意图），差距太大才 **substitution**（换实现路径，如 python-pptx 换成 PptxGenJS 以降低 tool_exec 要求）。一个 PPTX 技能的完整编译案例见 Figure 6。
2. **环境绑定（§4.2）**：编译器生成幂等的 env-binding 脚本，先静态分析依赖清单（对 59% 声明不完整的技能是必需的），再系统感知探测（pip、which）确认哪些依赖真缺，只在缺失时生成修复脚本。技能执行前先跑绑定脚本，环境中途变化时重跑；脚本失败才回退给模型处理。
3. **并发提取（§4.3）**：76% 的技能有显式过程结构，编译器用 LLM 把顺序散文分解成 workflow DAG（必须无环、无悬垂节点，否则丢弃）。按并行落点分三级：script-level（单步内并行处理多个数据项，无需 harness 支持）、tool-level（把相互独立的多个工具调用并进单次 LLM 轮次，要求 harness 支持批量工具分发）、agent-level（拆给子代理并行，要求 harness 支持子代理）。目标 harness 不支持时回退为顺序执行。

**JIT 运行时两个机制**（§5）：

- **自适应重编译**：运行失败分「任务特定」与「系统性」，只有系统性失败触发重编译。附录 A 给出准入门：每任务独立跑 R=2 次确认失败复现，改进需超过 δ=0.1 且编译后成本涨幅不超过 15%，任何基线任务回退超过 ρ=0.09 即出局。
- **代码固化（code solidification）**：75% 的技能含「整体形状固定、只有参数变化」的代码段。三阶段管线（Figure 8）：AOT 阶段生成 JIT 候选（触发关键词、代码签名、参数化模板、参数 schema）；运行时观察 LLM 生成代码，连续 N=3 次匹配签名才晋升（Algorithm 2）；之后模板直接实例化成可执行函数旁路模型推理。匹配失败累计 M=3 次则降级回 LLM 路径。晋升门槛当安全阀用：weather-forecast 任务因模型生成格式持续发散，永不晋升、一直走模型路径（Figure 14d）。

另有资源感知调度器（§5.3）：监视 429 限流信号节流新子代理，CPU/内存压力下暂停部分 agent-loop。

## 效果与代价

评估（§7）覆盖 8+2 个模型（从 claude-opus-4.6 到 devstral-small、qwen3-30b）、4 个 harness（BareAgent、OpenCode、OpenClaw、Codex）、SkillsBench + PinchBench 任务集，Mac Mini M4 16GB，每任务 5 实例 × 3 次取均值。基线四档：无技能 / 原始技能 / Skill-Creator 优化 / SkLLVM 编译。

主要数字（作者实测）：任务完成率平均提升 15.3%，token 消耗最多降 40%，wall-clock 加速至 3.2×，固化路径的执行延迟降 19-50×（PDF 提取 10.5-15.1 秒降到 0.2-0.57 秒，Figure 14）。弱模型受益最大：qwen3-30b +25%、devstral-small +10%（Figure 10）；BareAgent 上编译后各模型分差缩到 5 分以内。分阶段看（§7.3），AOT 编译让 14 类任务中 8 类平均提 88%，三轮 JIT 后 10/14 类满分；但 JIT 有回退风险，Line Chart 任务中编译器追加的示例文件过长触发解析错误，三轮才修复。成本侧（§7.3-7.5）：目标剖析 1.15M token 约 $7.92（每个 target 一次）；AOT 编译平均 90K token 约 $0.56 每技能；JIT 每轮约 $1。

代价与边界：强模型场景下提升主要变成省 token 而非提分（已有能力差距本就小，§7.2）；4.5% 的任务编译版反而低于原始技能，15% 无差异；tool-level/agent-level 并行分别要求 harness 提供批量分发与子代理机制，不支持的 harness 直接损失这部分收益；两个附录（重编译算法、固化状态机）标注为未经同行评审的补充材料。

## 总评

这是把编译原理的世界观完整搬到 Skill 生态的系统论文：能力剖面当 target profiling、技能变体当特化编译产物、固化当 JIT 热路径探测、失败准入门当 deoptimization 的反向守卫。它的工程价值在于把「技能在不同模型/harness 上表现漂移」从一个社区体感变成了可度量的三个失配轴，并给出对应的三条编译路径；对运营大规模 Agent 平台的团队，环境绑定与能力剖面这两件事不依赖整套 SkLLVM 也可以单独借鉴，前者解决的是 53% 技能都有的依赖声明缺失，后者把「这个模型到底会不会 X」变成了缓存可复用的离线测量。

需要打折扣的地方也明确。第一，编译器本体就是 LLM：能力分解、DAG 提取、重编译诊断全靠模型，论文用机械可查性质（无环 DAG、语法检查）加多次运行来压不确定性，但固化的代码只被检查「执行无异常且模型接受输出」（附录 B），不保证语义正确，错的模板只要不抛异常照样晋升。第二，收益分布高度偏斜：主要红利给了弱模型与脏环境，在强模型 + 满配环境里这套系统接近于一个省 token 的工程优化，$7.92 的剖析成本加每技能 $0.56 的编译成本要靠重复执行摊薄，个人轻度使用并不划算。第三，26 个原语能力与三级熟练度这套词汇表的可扩展性依赖持续的人工校准，论文自己承认能力集与边界「由设计者决定而非编译器固定假设」。

对本仓库读者，这篇与 agent_skills 目录的 Skill 编写实践互为镜像：那边讲怎么写好一个技能，这边讲技能进入异构执行环境后系统该怎么接住它。Claude Code Skills 的渐进式披露设计（metadata/instructions/resources 三层）正是本文分析的技能结构来源（§2.1 引 [7]），论文的三级并行也给出了 Skill 写作的新约束：想让编译器提取并行，步骤间的输入输出依赖要在行文里写清楚。

## 疑点与待核

- 评估任务集（SkillsBench、PinchBench）与训练用的能力微基准是否有重叠未说明；重编译准入门在 held-out 测试集上验证（附录 A），但能力剖面缓存与编译变体都见过同一 target 的剖析数据
- 固化的「语义正确性由模型检查」具体如何实现着墨少：Accept 返回模型裁决，模型的误判率没有单独量化
- Figure 11 中「AOT 编译后平均提 88%」的口径（哪些类、从多少分起）需要对着原图逐格核对
- 26 个能力覆盖 95% 需求是在 15,063 个过百下载技能上收敛的，长尾 89% 技能是否同分布未验证
