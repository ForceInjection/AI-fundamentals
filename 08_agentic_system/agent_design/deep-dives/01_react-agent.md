# Cursor IDE ReAct Agent 技术架构深度分析

> 本文基于 Cursor 官方公开资料（[docs.cursor.com](https://docs.cursor.com/)、[Cursor 博客](https://cursor.com/blog)）与 [ReAct 原论文](https://arxiv.org/abs/2210.03629)（Yao et al., 2022）整理分析，2026-11-14 核对。凡官方未公开数据（延迟、成功率、资源占用）本文不给出具体数字；涉及产品行为的表述以官方文档当时口径为准，迭代较快，使用前建议复核。

---

## 一、背景：AI 编辑器的两条路线

AI 辅助编程的产品形态在 2023 年之后分出了两条路线。一条是「Tab 补全」：模型预测你下一个要写的编辑，按键接受，节奏以毫秒计。另一条是「Agent 对话」：你用自然语言描述任务，模型自己读代码、改文件、跑命令，节奏以分钟计。两条路线对模型、交互和工程的要求完全不同，多数产品只做好其中一条。

Cursor 走的是第二条路线的重度形态。它由 Anysphere 开发，常见误解是「VSCode 插件」——实际上它是基于 Electron 深度定制的独立编辑器，内部直接改造了编辑器内核，这给了它做 Agent 所需的两个自由度：把编辑器状态完整暴露给模型，以及把模型输出直接写回文件系统。

Cursor 把产品理念概括为「tab-away the zero-entropy bits」：零熵的操作（机械重命名、样板代码、格式调整）交给模型预测，人只按 Tab。这句话值得当真，因为它定义了后面整个架构的取舍方向——预测得越准，人按 Tab 的次数越多；Agent 的自主性越强，人需要给出的信息越少。

## 二、问题：把 ReAct 搬进 IDE 要解决什么

[ReAct](https://arxiv.org/abs/2210.03629)（Reasoning + Acting）的核心是让模型交替地「想」和「做」：推理一步，执行一个动作，观察结果，再推理。范式本身简单，难的是落地到 IDE 这个具体环境时的四个工程问题：

1. **行动空间怎么设计**。IDE 环境里模型能做的动作有几十种候选（读文件、搜代码、跑终端、改文件……），哪些收进工具集、参数怎么约束、单轮允许调用多少次，直接决定 Agent 是可用还是失控。
2. **上下文怎么组装**。IDE 有海量状态：当前文件、光标位置、报错信息、Git 历史、整个代码库。全塞给模型不现实，全不给则寸步难行——哪些状态在什么时机进入上下文窗口，是 Agent 质量的最大变量。
3. **编辑怎么可靠落地**。模型生成的代码 diff 经常存在行号漂移、上下文不匹配的问题，直接写文件会造成破坏。谁来负责把「模型意图」可靠地变成「文件变更」，是独立于推理能力之外的另一个工程问题。
4. **信任边界在哪**。代码索引需要把代码片段交给云端模型，Agent 又要读写本地文件和终端。企业用户代码不出域的诉求与 Agent 能力之间存在天然张力。

Cursor 的架构就是围绕这些问题展开的。下面按「循环—行动—上下文—落地—模型」的过程叙事走一遍，第四个问题（信任边界）的答案放在第四章的取舍里讨论。

## 三、方案：从循环到模型的四层设计

### 3.1 循环骨架：推理与行动交替，先解释再行动

Cursor Agent 的每一轮执行遵循 ReAct 的交替结构：

```text
用户意图 + 编辑器状态 → 模型推理（决定下一步） → 工具调用 → 结果回填 → 继续推理 → … → 最终答复
```

与教科书式 ReAct 的一个差异在于用户可见性：Cursor 要求模型「先解释再行动」——每次调用工具前，先用自然语言向用户说明为什么这么做。用户看到的是一段连贯的叙述，工具调用发生在叙述之间的后台。这个设计把 ReAct 的「推理轨迹」从日志变成了产品体验的一部分：用户能随时打断方向错误的 Agent，而不是等它跑完才发现理解错了。

### 3.2 行动空间：工具集、JSON Schema 与调用上限

Agent 模式的行动被收编为一组封闭工具，全部以 JSON Schema 声明参数，模型输出符合 schema 的调用命令才能执行：

- **搜索类**：`codebase_search`（语义搜索）、`grep_search`（正则精确匹配）、`file_search`（文件名模糊查找）——三种搜索覆盖「不知道代码长什么样」「知道关键字」「只知道文件名」三种场景
- **文件类**：`read_file`（按行读取）、`list_dir`（目录探索）、`edit_file`（增量编辑）、`delete_file`
- **执行类**：`run_terminal_cmd`（终端命令，高风险操作需用户批准）
- **扩展类**：MCP 协议（stdio / SSE / HTTP）接入外部服务，第三方工具以同样的 schema 机制注入对话

约束不只来自 schema。官方文档对 Agent 模式设有单轮工具调用次数上限（25 次口径，随版本变化），这个上限是「自主性」的硬边界：任务在预算内完成不了，模型必须回来向用户说明，而不是无限循环下去。对照 ReAct 论文里允许的开放式循环，这是产品化时的关键收缩——失控的 Agent 在 IDE 里意味着真实的文件破坏。

### 3.3 上下文组装：意图与状态分离，四层来源，Merkle 树索引

Cursor 把上下文分成两类。**意图上下文**回答「用户想要什么」：自然语言指令、系统提示词、项目规则文件（`.cursorrules`）。**状态上下文**回答「世界现在什么样」：代码内容、报错与 Lint 结果、光标位置、Git 历史。这个区分决定了两者的组装策略——意图由用户显式给出，状态由系统自动收集。

状态上下文的收集分四层：

1. **即时层**：当前编辑文件内容与光标位置，逐字进入
2. **语义层**：通过 AST 分析找到的相关函数、类片段
3. **工程层**：向量检索整个代码库里与任务最相关的片段
4. **历史层**：Git 历史提供的演变信息

工程层的基础设施是代码库索引。Cursor 用语义分块（基于 AST 切分）生成代码块向量，以内容哈希为键缓存；跨文件的变更检测用 Merkle 哈希树管理——文件变更只影响树上的一条路径，增量更新成本与变更量成正比而非代码库规模。这套索引同时服务语义搜索与多人协作时的索引同步。

进入窗口的优先级也有明确顺序：用户显式指定的文件与符号 > 当前编辑位置 > 语义搜索结果 > 最近访问文件 > 项目配置。超出窗口时按优先级裁剪。

### 3.4 编辑落地：主模型与 Apply Model 分离

这是 Cursor 架构里最值得单独拆出来的一步。主 Agent 生成的是**编辑意图**（对哪段代码做什么改动），不是最终文件内容；真正把意图应用为文件变更的是专门的 **Apply Model**（代码应用模型）。分离的理由很实际：擅长规划的强推理模型在「逐字生成完整文件」这类机械任务上又慢又贵，而应用 diff 需要的是严格与快速——一个专门的小模型做得更好。

两个配套机制让落地更稳：

- 增量编辑使用 `...existing code...` 标记保留未改动的上下文段落，模型只描述变化部分，应用模型负责对齐定位
- 应用效果不佳时，`reapply` 工具用更强的模型重新应用同一份意图——把「重试」做成了显式工具而非隐藏逻辑

这条「推理模型与应用模型分离」的路线是 Cursor 较早的产品化实践，此后「规划模型与应用模型各司其职」的分工方式在 AI 编码产品中被广泛采用。

### 3.5 模型分工：按任务类型路由

Cursor 不绑定单一模型，而是按任务特征路由：复杂规划与重构用强推理模型（Claude 系列、GPT 系列、Gemini、Grok 等可选），Tab 补全用低延迟专用模型，代码应用与搜索重排序各有专门模型。路由的依据是任务的复杂度与延迟要求——补全要的是毫秒级响应，重构要的是推理深度，两者在同一个编辑器里并行存在，互不阻塞。

## 四、取舍与边界

### 4.1 自主性的收缩

ReAct 论文里的 Agent 理论上可以无限循环。Cursor 把它收缩为「有限预算下的自主」：单轮 25 次工具调用上限、终端命令的用户批准机制、编辑前的 diff 预览。每一条收缩都牺牲一点自动化程度，换回一点可控性。对 IDE 场景这个取舍是对的——用户就在屏幕前，打断的成本几乎为零；对无人值守场景（CI 里的自动修复）同样的收缩就会显得束手束脚。

### 4.2 隐私与信任边界

代码库索引要把代码片段交给云端模型，这与「代码不出域」的企业诉求直接冲突。Cursor 的缓解手段是显式的隐私模式（privacy mode：开启后代码不用于训练，索引走临时存储）与 SOC 2 合规认证；企业版提供 SSO 与团队级配置。边界依然存在：隐私模式下语义检索仍依赖云端索引服务，完全离线的代码补全能力是降级的。对敏感行业的团队，「部分信任」与「完全不出域」之间的落差需要在采购评估时显式对待，而不是被「SOC 2 认证」一句话带过。

### 4.3 数据声明

官方没有公开 Agent 各环节的延迟、成功率与资源占用数据，本文因此不给出此类数字。市面上流传的「内存降低 30%」「成功率 99.5%」一类说法多无出处，引用前建议要求来源。

## 五、总评

**这套架构回答对了什么**：Cursor 把 ReAct 从论文范式做成日常工具，靠的是四个收敛而非发明——工具集收敛为带 schema 的封闭集合，上下文收敛为四层优先级，编辑落地收敛给专用 Apply Model，自主性收敛进 25 次调用预算。每个收敛都对应一个真实故障模式（格式失控、上下文爆炸、diff 写坏文件、无限循环），这种「对着故障做设计」的思路比任何单点技术更值得借鉴。

**它没有回答什么**（折扣清单）：

- 各环节性能数据官方未公开，本文与市面上文章都没有可靠数字
- 单仓库内的 Agent 能力已较成熟，跨仓库、跨服务的大规模变更仍是弱项
- 上下文组装对检索质量依赖重，索引没建好或历史欠账多的代码库，语义层贡献会明显下降
- 隐私模式与完全离线之间仍有能力落差，强合规场景需要另行评估

**何时值得对照这套架构**：自建编码 Agent 或任何「模型 + 文件系统」类工具的 Agent 时，Cursor 的四个收敛（封闭工具集、分层上下文、意图与应用分离、有限预算）都是可直接复用的设计检查单。
