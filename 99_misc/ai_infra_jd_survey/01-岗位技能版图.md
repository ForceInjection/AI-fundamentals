# 312 条 JD 里的 AI Infra 技能版图

> 数据集：312 条在招岗位说明（JD），采集于 2026-11-18；其中 JD 全文 263 条、搜索快照摘要 49 条。文中数字均以采集日为准。

想整理一份 AI Infra 方向的学习材料索引时，遇到一个问题：该学什么、按什么顺序学，现有的说法基本靠个人印象。「推理引擎是核心」「K8s 必须会」这类判断对不对、有多普遍，需要一个市场口径的坐标系。岗位描述（JD）是现成的坐标来源：每一家公司为想要的能力标了价，写明了要求。于是我们把能抓到的 AI Infra / Agent 相关 JD 抓了下来，数了一遍。

这份劳动的产出是一个可复用的数据集和三样衍生物：分类报告、技能树、一张可交互的技能版图页面（[visualization.html](visualization.html)）。这篇文章讲清楚三件事：数据怎么来的、市场呈现出的样子、以及从 JD 到学习路线是怎么推导的。

## 一、数据怎么采的

312 条 JD 来自三个层级的渠道，完整度不同：

| 层  | 渠道                                              | 条数 | 完整度       |
| --- | ------------------------------------------------- | ---- | ------------ |
| 1   | 国内大厂官网招聘接口与页面                        | 179  | JD 全文      |
| 2   | Hacker News「Who is hiring」月帖（2026-09 至 11） | 74   | 多为全文     |
| 3   | BOSS 直聘/猎聘/脉脉的搜索快照 + 公开文章          | 59   | 快照摘要为主 |

采集分两轮。第一轮是常规 HTTP 与 API 直抓：字节、腾讯、蚂蚁、百度、美团、阿里的招聘站都有公开 JSON 接口，逐条拿到结构化的岗位职责与任职要求；HN 帖通过 Algolia API 一次拉全，按关键词筛出 AI infra / agent 相关岗位。第二轮用 Playwright 无头浏览器补抓第一轮拿不到的纯前端渲染站点：月之暗面、智谱的岗位列表挂在 Moka 投递站上，华为、快手的详情页需要渲染后才出内容，这一轮补进 40 条全文。

原则只有一条：取页面正常展示给访客的内容，职责与要求逐条照抄原文，抓不到就记录原因并放弃。没有绕过任何登录墙、接口加密或人机验证。百度详情页（登录墙加反爬跳转）、米哈游（TLS 连接失败）、拉勾（WAF 且不被搜索引擎收录）、京东校园（接口加密）四个渠道最终没有产出，这里如实记录。

49 条快照记录只保留快照里真实可见的字段，公司名没显示的就留空。它们不参与后文的技能词频统计。

## 二、市场长什么样

**类别分布**：研发 225 条（72%），测试 35 条（11%），SRE 24 条（8%），运维 24 条（8%），算法 3 条。研发岗占绝对多数，但三个非研发方向加起来接近三成，AI Infra 的「运维侧」已经是一个成建制的岗位族，不再是「顺便管管服务器」。

**公司分布**：腾讯 46 条（四类全覆盖，其中 SRE 13 条是全部样本里最大的 SRE 招聘方）、字节跳动 43 条（研发 24 条）、蚂蚁集团 20 条（测试 10、SRE 5、运维 5）。之后是美团 13、月之暗面 11、百度 10、阿里 10、智谱 10、快手 10、寒武纪 9、华为 7。模型公司（月之暗面、智谱、MiniMax）全部集中在研发侧；测试与运维岗位几乎全部来自大厂平台部门。完整的类别×公司交叉表在分析报告（`analysis/classification.md`）中。

**地域**：北京约三分之一（115 条，含「北京市」写法），深圳 35、杭州 21、上海 18。海外岗位来自 HN 帖，散布在旧金山、柏林、远程。

**研发内部的细分方向**还有一个信号：Agent 平台 45 条是最大单方向，超过 ML 平台（30）与推理引擎（21）。推理相关岗位的名字高度分散，「推理引擎」「推理优化」「推理性能优化」「推理 Runtime」等十余种写法合计约 40 条，实际体量与 Agent 平台相当。命名碎片化是生态早期的常态：方向已经成型，职级体系和岗位命名还没统一。

招聘类型上，社招 265 条占绝对多数，校招 8、实习 8。AI Infra 的供给目前主要靠社招转会，校招入口还很少。

## 三、技能版图

对 JD 全文的技能标签做归一化统计（Kubernetes/K8s 合并、LLM 与大模型合并等）之后，全局 Top 10：

| 排名 | 技能       | JD 数 | 占 312 条比例 |
| ---- | ---------- | ----- | ------------- |
| 1    | Python     | 155   | 50%           |
| 2    | Kubernetes | 71    | 23%           |
| 3    | 大模型/LLM | 62    | 20%           |
| 4    | C++        | 61    | 20%           |
| 5    | CUDA       | 55    | 18%           |
| 6    | vLLM       | 53    | 17%           |
| 7    | Linux      | 50    | 16%           |
| 8    | Agent 框架 | 48    | 15%           |
| 9    | Go         | 45    | 14%           |
| 10   | PyTorch    | 43    | 14%           |

Python 过半数，是唯一一项跨所有方向的技能。K8s 排第二，说明 AI Infra 的底座已经迁移到云原生调度。真正把 AI Infra 与传统后端区分开的是第 3 到第 6 名：大模型、CUDA、vLLM 这三项在传统后端 JD 里几乎不出现。

四条线的技能画像差异更值得看：

- **研发线**（225 条）：Python(100)、C++(61)、CUDA(45)、vLLM(44)、Kubernetes(42)、PyTorch(40)、SGLang(34)、模型量化(32)。语言和引擎并重。
- **测试线**（35 条）：大模型/LLM(28)、Python(27)、Agent 框架(20)。AI 测试已经不是点 Selenium 那套，评测对象本身变成了模型和 Agent，Prompt 工程(4) 也进了技能表。
- **SRE 线**（24 条）：Python(21)、故障排查(17)、Kubernetes(16)、GPU 运维(11)、SLA/SLO(10)、可观测性(8)。
- **运维线**（24 条）：故障排查(11)、GPU 运维(10)、监控告警(8)、RDMA(4)、Prometheus(3)。

SRE 与运维两条线高度趋同，核心组合都是「GPU 硬件 + 故障排查 + 监控」，差别在 SRE 多了服务稳定性方法论（SLA/SLO、可观测性），运维多了网络组网（RDMA/InfiniBand）与机房侧内容。

技能共现统计（同一条 JD 同时要求两项技能）给出了绑定关系：C++ + Python 共现 51 条，是研发岗的基本盘组合；SGLang + vLLM 共现 33 条，推理引擎双修已经是推理岗的默认要求，只会一个不够。

## 四、四条学习路线

从频次到路线还差一步：频次说「什么重要」，顺序要说「先学什么」。我们把每条线整理成「底座 + 分方向路线」两层：底座是该线几乎所有 JD 都要求的技能，分岔之后每个方向从左到右是建议的学习顺序。

- **研发线**：底座 Python、Linux、Docker。之后分四条岔路：推理引擎方向（C++ → CUDA → vLLM → SGLang → 模型量化 → KV Cache → Triton）、Agent 平台方向（TypeScript → LangChain → LangGraph → RAG → MCP → Evals）、训练框架方向（PyTorch → Megatron → DeepSpeed → NCCL → 分布式训练）、ML 平台方向（Go/Java → Kubernetes → Ray）。
- **测试线**：底座 Python、Java、Linux，主干是自动化与 CI/CD，AI 专项按大模型 → Agent 框架 → RAG → Prompt 工程展开。
- **SRE 线**：底座 Linux、Shell、Python，先平台稳定性（K8s → 监控 → 可观测性 → SLA/SLO → 故障排查），再 AI 专项（GPU 运维 → NCCL → vLLM/SGLang → KV Cache）。
- **运维线**：底座 Linux、Python，先 GPU 硬件与故障排查，再监控与网络（RDMA），最后推理服务。

必须说明：这个顺序是编辑判断，依据是 JD 频次与技能间的依赖关系（底层语言先于框架，框架先于调优），JD 原文本身没有顺序。它是一个整理学习材料的骨架，不是权威课表。

着色之后还有一个意外发现：给技能按家族分色（语言、引擎与框架、平台与设施、AI 专项）时，推理引擎线的配色是「蓝 → 蓝 → 黄 → 黄 → 绿」：先两块语言（C++、CUDA），再两块引擎（vLLM、SGLang），再 AI 专项；Agent 平台线则是「蓝 → 黄绿交替」，几乎没有平台层。两个方向的技能构成差异，在颜色上直接可见。

完整的交互版在 [visualization.html](visualization.html)：四条线可以切换，每个技能块标注 JD 数，技能谱系树可以逐层展开。

## 五、方法与口径的边界

- **快照口径**：49 条聚合平台快照只填可见字段，未参与词频统计；词频全部基于 263 条全文。快照里的薪资等字段与实时数据可能有出入。
- **命名碎片化**：研发细分方向有 59 种写法，本文只归并列出量级，未做强行合并；推理类的真实体量比单看「推理引擎(21)」要大。
- **地理归一粗糙**：「北京」与「北京市」未合并统计，文中引用时做了手工说明。
- **平台代表性**：BOSS 直聘等登录墙平台只能拿到搜索快照，样本向官网公开渠道倾斜；技术岗官网化程度高，偏差可控但没有精确估计。
- **HN 帖拆解**：海外 JD 是自由文本，职责与要求的拆解粒度与国内结构化字段不完全一致，跨海内外的对比只做方向级。

## 六、数据与方法

支撑这篇文章的是三样东西：312 条结构化 JD（`data/jd_2026-11-18.jsonl`，15 字段 schema，逐条带 `source_url` 可追溯原页）、分析脚本（`scripts/`，分类统计、技能树、共现矩阵，技能归一化映射也在其中）和两份分析报告（`analysis/classification.md`、`analysis/skill-tree.md`）。数据 schema 与采集方法在 [README.md](README.md) 里有完整说明，本文的每个数字都出自那份分析报告。

交互版在 [visualization.html](visualization.html)：四条线可以切换，每个技能块标注 JD 数，技能谱系树可以逐层展开。

数字是采集日（2026-11-18）的快照。招聘市场的变化会让这份版图里的一部分结论过期，技能的相对排名尤其如此；「四条线各自需要什么」这类结构性判断衰减得慢得多。
